# 核心技术实现

> 三个核心技术的深度剖析:① 通过骨架生成虚拟人知识库;② 骨架的增删改查;③ 知识库渐进式加载。
> 所有代码位置均给出文件与函数名,可直接对照源码阅读。

## 1. 通过骨架生成虚拟人知识库

### 1.1 问题定义

输入:一份**人生履历骨架**——外部 JSON 事件数组(每条含 `start/event_type/payload`),典型规模几十到两千条。例如:

```json
[{"type": "买房", "start": "2010", "payload": {"房子": "县城两居室", "总价": 180000}},
 {"type": "女儿出生", "start": "1998", "payload": {"胎次": 1}}]
```

输出:一个完整可对话的虚拟人,包含五类产物——

| 产物 | 表 | 形态 |
| --- | --- | --- |
| 人物骨架 | `persona.core_identity / name` | 250-450 字档案 |
| 性格导向 | `persona.personality` | 第二人称写作提示词 |
| 情景记忆 | `episodic_memories` | 每事件一条第一人称回忆(150-300 字) |
| 履历展开 | `life_scaffold_contents` | 每事件摘要+第三人称正文(1:N) |
| 知识节点+财务 | `kb_nodes/kb_node_contents` + `finance_events` | 主题化知识与可挂账大事 |

**难点**:① 履历多则上下文爆炸;② LLM 流式输出大 JSON 必截断;③ 内容审核会拦截部分敏感文本;④ LLM 会漏事件、编金额。本方案的解法分别对应下文四小节。

### 1.2 总体流水线(LangGraph 状态机)

编排器 `vh_generate/generate/scaffold_graph.py` 定义五节点状态机:

```
START → ensure_skeleton → ensure_personality → fetch_batch ─┬─(有 pending)→ generate_memories ─┐
                                                             └─(无 pending)→ expand_events → finalize → END
                                                                  ↑──────────────────────────────┘
```

设计要点:

- **节点逻辑与 IO 解耦**:节点实现打包成 `ScaffoldHandlers` dataclass 由上层(`vh_api/main.py` 的 `scaffold_generate`)注入,`scaffold_graph` 模块不依赖 `vh_api`,避免循环依赖。
- **Postgres checkpointer**:`compile_scaffold_graph(handlers, checkpointer=AsyncPostgresSaver)`,`thread_id = scaffold-{persona_id}`。进程崩溃/服务重启后按 thread_id 续跑,状态(messages + metadata)持久在 PG。
- **进度流**:`graph.astream(init, cfg, stream_mode="updates")` 逐节点回报,job_service 把进度写入任务状态(percent/message/logs)。
- **防死循环**:`h_generate` 发现本批 `saved == 0` 时向状态写入 `error="no_progress"`,条件边终止。

### 1.3 第一步:骨架与性格归纳(增量归并 map-reduce)

`generate_skeleton_async` / `generate_personality_async`(`scaffold_gen.py`)。核心是 `run_incremental_summary`(`progressive.py`):

```
阶段笔记 notes = ""
for 第 no 批 (履历按年份排序, 每批 10 条):
    上下文 = system + 任务描述 + 年份分布直方图 + 阶段笔记 + 本批全文
    notes  = LLM("把本批新信息合并进笔记后输出更新版笔记")[-2000:]
最终: 依据 notes 输出骨架档案 (姓名/性别出生/籍贯/职业轨迹/关键经历/现状/性格初判)
```

关键细节:
- **每次调 LLM 的上下文长度恒定**(system + ≤400 字笔记 + 10 条),与履历总量无关,400 条履历也不撑爆 prompt。
- **笔记截断 `[-2000:]`** 只留更新版本身,防累积膨胀。
- **年份分布直方图**(`RangeFeed.overview`)放进首条消息,LLM 不读明细也能感知全局。
- 骨架生成后正则抽取「姓名:」回填 `persona.name`(履历无名时 LLM 依据性别/年代/地域起自然中文名,占位名判定后覆盖)。

### 1.4 第二步:事件 → 情景记忆(tool-calling 渐进消化)

`process_scaffold_events_async`(`scaffold_gen.py`)。这是流水线的心脏:

**① 工具即落库协议**。LLM 绑定 `RecordMemoryArgs` 工具,一条事件一次调用:

```python
class RecordMemoryArgs(BaseModel):
    event_id: str      # 原样回传 (校验 + 防张冠李戴)
    title: str         # 如 "女儿出生那年冬天"
    content: str       # 第一人称回忆 150-300 字
    occurred_at: str   # YYYY-MM-DD
    emotion: str       # 喜悦/焦虑/怀念…
    summary: str       # 事件档案摘要 (第三人称)
    detail: str        # 事件档案正文 (第三人称)
```

每批 5 条事件一次 LLM 调用,模型对每条事件返回一个 tool_call。**不让 LLM 输出大 JSON**——工具参数经 Pydantic 校验,逐条即时落库,单条失败不影响其他。

**② 落库与游标推进**(每条 tool_call 的处理):

```
EpisodicMemory (content=第一人称, summary, occurred_at, importance=6)
LifeScaffoldContent (event_id, seq=0, summary, content=detail)   ← 履历展开
mark_processed(event_id, mem.id)                                  ← 游标 + 回链
```

`processed=True` + `memory_id` 回链构成**批次游标**:任何时刻中断,下次 `fetch_pending_batch` 都从未处理事件继续——幂等性的基石。

**③ 审核拦截三级降面**(不 fail-fast):

```
整批调用 (5 条) 被拦截(400 inappropriate)
  → 降级: 逐条单独调用 (上下文更小)
      → 单条仍被拦截
          → 本地模板兜底: 从 payload 字段直接拼一条基础记忆落库
            + mark_sensitive(event_id)   ← 黄色标记, 此后不再送 LLM
```

模板兜底保证**进度永不卡死**;敏感事件在后续归纳步骤(`finalize`)中只保留概要行、不参与 LLM 送审。

**④ 漏事件检测**:LLM 未覆盖的事件(id 不在 `handled` 集合)统一走模板兜底并标记 processed,保证「事件数 = 记忆数」的完整性不变量。插入式生成(`scaffold/insert` 接口)还会**落库后校验**:未 processed 的重试一次,仍失败则补生成展开内容。

**⑤ 流式重试封装** `astream_merged`(`progressive.py`):流式收完整 AIMessage(多个 chunk 相加合并 tool_calls),`_is_content_blocked` 识别审核/超限/掐断类异常(类型名 + 关键字匹配),重试一次后放弃返回 None,由调用方降级。**非拦截异常直接 raise**,不吞真错误。

### 1.5 第三步:履历展开与收尾

**expand_events**:为每条事件生成 `life_scaffold_contents`(摘要 + 第三人称正文),`RecordEventContentArgs` 工具协议;`force=True` 删旧重生成;有进展时对 LLM 漏掉的剩余事件**递归重试**。

**finalize**(归纳知识节点 + 抽取财务大事记)是最精细的一步:

**① 敏感过滤 + 组批**:敏感事件只留概要行;履历按 10 条/批,按批内年份区间带上**同年段的记忆**与**财务候选**;剩余记忆单独成批。

**② 财务候选编号防张冠李戴**(`_money_candidates`):

```
履历事件 payload → 命中金额字段(彩礼/房价/学费/贷款…) 或 ≥1000 的数值
              → 生成候选 {ref: "F1", year, amount, hits: ["彩礼=88000"]}
```

系统提示强制:`event_ref 必须填清单编号; 金额/年份必须与清单完全一致; 不得自己新增事件`。落库时**每个候选确定性入账**——LLM 只提供标题/类型/分类的润色(`llm_fin.get(ref)` 缺省走 `_infer_fin` 规则推断),金额永远来自候选而非 LLM 输出。另有规则:

- `_pick_memory`:按标题匹配/年份最近原则把财务事件挂到情景记忆(`memory_id` 外键必填);
- `(title, amount, year)` 去重;仅当履历**完全没有**可提取金额时才接受 LLM 自报的财务事件;
- `non_money_keys`(身高/体重/面积…)显式排除非金额数值。

**③ 知识节点收敛**:
- 每批归纳 0-3 个节点(无新信息不记),`node_type` 限四类,标题 6 字内,正文 200-500 字;
- **节点总量封顶 12 个**(`n_nodes >= 12` 跳过),防分批重复堆叠;标题去重(`seen_titles`);
- **幂等清理**:先 `DELETE FROM kb_nodes WHERE tags->>'source' = 'scaffold'` 与 `note='scaffold'` 的财务,再重生成——只清本流程产物,不动人工录入;
- 生成的节点 `slug = "scaffold-kb-{idx}-{标题转写}"`,`tags={"source": "scaffold"}`。

**④ 骨架索引回写**:`persona.bio_skeleton = "\n".join('<slug id="{pid}/{slug}">{title}</slug>')` 按 importance 降序——**人生骨架 = 知识节点标题索引**,用 `<slug>` 标签引导模拟 agent 按需探索(见 §3)。

### 1.6 正确性设计小结

| 风险 | 机制 |
| --- | --- |
| LLM 编造金额 | 金额只能来自履历候选编号,确定性入账 |
| LLM 漏事件 | handled 集合检测 → 模板兜底;插入场景落库后校验重试 |
| event_id 张冠李戴 | `by_id` 白名单校验,未知 id 跳过 |
| 审核拦截卡死 | 三级降面 + sensitive 隔离(黄色,不再送审) |
| 重复堆积 | finalize 幂等清理(tags/note 标记来源);财务三元组去重 |
| 中断丢失 | processed 游标 + memory_id 回链 + PG checkpointer |

## 2. 骨架的增删改查

### 2.1 数据模型

`scaffold.py` 的两张表:

```
life_scaffold_events                        life_scaffold_contents
─────────────────────────                   ───────────────────────
id (uuid36 PK)                              id (uuid36 PK)
persona_id FK → persona (CASCADE)           event_id FK → life_scaffold_events (CASCADE)
ord (导入顺序)                               persona_id FK (CASCADE)
event_type (≤32)                            seq (一事件多展开)
start_year / start_raw / end_year           summary (30-60 字)
payload (JSONB, 容错解析)                    content (120-300 字)
causes (JSONB)
world_event_ref / source / confidence
visibility / correction_of / schema_version
processed (bool, 游标)                       ← 消化状态
sensitive (bool, 审核标记)                   ← 黄色隔离
memory_id → episodic_memories               ← 产物回链
```

索引:`(persona_id, start_year, ord)` 支撑按时间排序取批;`(persona_id, processed)` 支撑 pending 批查询。

`_new_event` 做**外部 JSON 容错**:兼容 `type/event_type`、`start/start_year`;`start_raw` 保留原文、`start_year` 正则抽取 4 位年份;`payload/causes` 是 JSON 字符串时自动解码。

### 2.2 查(Read)

| API | 实现 | 说明 |
| --- | --- | --- |
| `GET /api/personas/{pid}/scaffold` | `scaffold_service.list_events` | 事件 + 聚合展开内容 + persona 三段(骨架/性格) + 进度 stats |
| `GET /api/personas/overview` | main.py | 全人物计数卡片(事件/已消化/展开/节点/财务/记忆) |
| `stats()` | scaffold_service | `{total, processed, pending, year_from, year_to}` |

`list_events` 一次取事件表 + 全部 contents,按 `event_id` 分组挂到每条事件的 `contents` 字段,首块摘要/正文提升为 `summary/content` 快捷字段——前端时间轴一查全得。

### 2.3 增(Create)与改(Update):三策略写入

核心是 `scaffold_service.apply_events`,一个函数承载三种时间维度策略:

```python
apply_events(persona_id, events, strategy=..., payload_mode=...)
```

| strategy | 语义 | 实现 |
| --- | --- | --- |
| **insert** | 仅追加(允许重复) | 逐条 `_new_event`,`ord` 接在现有最大值后 |
| **replace** | 覆盖入参年份区间 | 删除 `[min_year, max_year]` 内旧事件(连带记忆/展开)后插入 |
| **merge** | 同年份+同类型合并 | 命中则更新字段并合并 payload;未命中则插入 |

**级联清理的完整性**(`drop_event` / merge 更新分支)——删除或合并一条旧事件时,同事务内:

```
memory_id 非空 → 删除关联 EpisodicMemory
删除该事件的全部 LifeScaffoldContent
删除/重置事件行本身
```

保证**不存在指向已删记忆的悬挂事件、不存在孤儿展开内容**。

**merge 的重消化语义**:合并后 `processed=False`、`memory_id=None`、删旧产物——该事件进入下一轮 `fetch_pending_batch`,会重新生成记忆。`payload_mode=merge` 为浅合并(新值覆盖旧值),`replace` 整体替换。

### 2.4 删(Delete)

`DELETE /api/personas/{pid}/scaffold/events/{event_id}` → `delete_event`:校验 `(persona_id, event_id)` 双键归属后,同 §2.3 的级联清理删除。人物级删除依赖 PG 外键 `ondelete="CASCADE"` 全链自动清理。

### 2.5 增量再生成(改后的一致性维护)

`POST /api/personas/{pid}/scaffold/insert?generate=true` 触发后台 job,三段式:

```
① apply_events 落库 → 返回受影响 event_ids
② 逐批 process_scaffold_events_async(5 条/批) + 落库后校验(未 processed 重试一次,
   仍失败补 expand) — 只处理受影响事件, 不重刷全量
③ finalize_persona_async — 幂等重建知识节点与财务大事记
   (先删 tags.source=scaffold / note=scaffold 的旧产物再生成)
```

**一致性模型**:事件级产物(记忆/展开)随事件增删改**精确联动**;人物级产物(知识节点/财务)**整体重建**——因为主题归纳本质是全局函数,增量维护比幂等重建更不可靠。重建用来源标记(`tags`/`note`)划清边界,**永不误删人工录入的节点**。

### 2.6 单条重生成与人工修订

| 场景 | API / 实现 |
| --- | --- |
| 单条履历展开重生成 | `POST …/scaffold/events/{event_id}/expand` → `expand_scaffold_events_async(batch_size=1, force=True, event_ids=[id])` |
| 人物骨架重生成 | `POST …/skeleton/generate` → 增量归并重跑(后台 job) |
| 人工修订骨架 | `PUT …/skeleton` 直接写 `core_identity + bio_skeleton` |
| 性格导向重生成/修订 | `POST …/personality/generate` / `PUT …/personality` |
| 全量重新导入 | `POST …/scaffold/import` → `save_events`(先清空该人物旧事件再落库) |

所有 LLM 参与的长操作都是**后台 job + 轮询**模式(`job_service`):运行态在内存 dict(高频更新不写库),终态落 `jobs` 表(percentage/logs/result 供回看);`spawn_job` 登记任务集合,应用 shutdown 时统一取消,避免 asyncio 悬挂任务。

## 3. 知识库渐进式加载

### 3.1 设计动机与 L0/L1/L2 模型

虚拟人一生的记忆与知识可能有几百 KB 文本,而对话窗口只有几千 token。方案是**三级渐进**:

| 层 | 内容 | 体量 | 装载方式 |
| --- | --- | --- | --- |
| **L0** | `persona.core_identity` 身份自述 + voice_style + `<slug>` 骨架索引(bio_skeleton) | 数百 token | **常驻** system prompt |
| **L1** | kb_nodes 的 `title + summary`(每节点 ~100 token) | 随节点数 | 树/骨架浏览, 检索默认层 |
| **L2** | kb_node_contents 正文块全文(单块 1-3KB)、EpisodicMemory 全文 | 大 | **命中才装**, 预算控制 |

存储侧的支撑是**冷热分离**:`kb_nodes` 热表无正文(L1 扫描快),`kb_node_contents` 冷表 1:N 存块(L2 命中才 join)。检索单元 = 加载单元 = 内容块。

`persona.bio_skeleton` 里的 `<slug id="persona_id/slug">标题</slug>` 标签是 L0→L1 的**寻址机制**:agent 在常驻上下文里看到标题索引,用 slug 精确拉取 L1/L2。

### 3.2 检索装载管线(`kb/retrieval.py` + `kb/async_api.py`)

`retrieve_context / aretrieve_context` 是渐进加载的检索侧入口:

```
query
 │ ① 骨架先行 (可选, 也占预算)
 ▼
② 向量召回: kb_embeddings HNSW cosine → top_k=20
   (嵌入可选: vh_generate 启动时 register_embedder 注入;
    未启用 → 词面相似度降级: 中文二元组+英文词 token, 覆盖度+标题加权)
 │
 ▼
③ load_score 打分 (每个候选块):
   score = 0.5·相似度 + 0.2·(importance/10) + 0.2·exp(-天数/30) + 0.1·min(access_count/20, 1)
                                            └ 30 天半衰期的新近度    └ 20 次封顶的强化
 │
 ▼
④ _fill_context 预算装载 (五重约束):
   绝对阈值   score < 0.16 不装
   相对阈值   score < top_score × 0.6 不装
   分类配额   内容块 ≤6 / 情景记忆 ≤10
   近重复过滤 同类 Jaccard ≥0.80 / 跨类 ≥0.55 视为重复跳过
   token 预算 不得超过 persona.context_token_budget − 已用
 │
 ▼
⑤ 访问记录回写: 命中块 access_count+1, last_accessed_at=now (块级+节点级联动)
   + memory_access_log (trigger=retrieval) → 反过来影响下一轮 ③ 的打分
```

**这是一个记忆系统而非搜索系统**:检索会回写访问记录,「常被想起的记忆」获得强化分,「久未想起的记忆」新近度衰减——类遗忘曲线,数据闭环。

### 3.3 节点级渐进 API

| API | 层级 | 语义 |
| --- | --- | --- |
| `get_node(persona_id, slug, load_level)` | 1 / 2 | 1=title+summary;2=全部内容块全文(命中联动 access 计数+日志) |
| `get_kb_tree(persona_id)` | L0/L1 | 虚拟根 + parent_id 组装,`render()` 输出树形文本 |
| `get_node_clues(persona_id, slug)` | L1 | kb_edges 双向联想线索(related/causes/contradicts/elaborates/part_of),按 weight 降序——**联想加载**:看 A 的线索即可决定是否拉取对端节点 |
| `arender_persona_md(...)` | L0/L1 | Markdown 简介;`disclosure_level≥min_disclosure` 才输出 summary,0 视为隐藏(`<slug disclosed="false"/>`),未披露节点只列标题 |

同步版 `kb/retrieval.py` 与异步版 `kb/async_api.py` 一一对应;异步版是主路径(psql async + SelectorEventLoop),树组装等纯内存逻辑两版共用。

### 3.4 Agent 侧渐进回忆(PersonaAgent 工具协议)

`vh_simulate/simulate.py` 把渐进加载暴露为 **agent 的回忆工具**,让 LLM 自己决定何时深入:

| 工具 | 层级 | 用途 |
| --- | --- | --- |
| `LoadTreeArgs` | L0(默认)/L1 | 看知识树结构,最省 token |
| `LoadSkeletonArgs` | L1 | 骨架与节点索引 |
| `RetrieveContextArgs` | L1(默认)/L2 | 按问题检索(§3.2 管线) |
| `LoadContentArgs` | L1/L2 | 读某节点(标题或 slug 定位) |
| `RecallMemoryArgs` | L1/L2 | 读某条具体情景记忆(标题或 id) |

系统提示明确渐进纪律:**「先 L0/L1 浏览,选中少量目标再读 L2;不要默认大量拉全文」**。`RetrieveContextArgs` 的 L1 模式返回「命中块摘要 + slug/id」清单,并附提示「需要全文时用 LoadContentArgs/RecallMemoryArgs (level=2)」——**两段式加载**:第一段廉价探查,第二段精确取文。

`PersonaAgent.create(brief=True)` 的常驻上下文只有:L0 身份 + 骨架索引 + 财务账本;节点/记忆全部交给工具按需加载。每轮 `_recall` 的检索事件(blocks/score/used/budget)通过 `on_event` 回调外抛,前端可视化「agent 想起了什么」。

### 3.5 生成侧的渐进读取(RangeFeed + 折叠)

渐进思想同样贯穿**铸造侧**(`progressive.py`)——解决「履历/记忆几百条一次性塞 prompt 会超上下文且易触发审核误判」:

**① RangeFeed 范围视图**:

```python
RangeFeed(title="人生履历", items=[...], year_of=..., render=单条一行, digest=一批一行概要)
```

- `overview()`:年份分布直方图(不含明细),agent 据此规划读取范围;
- `query(start_from, start_to, limit≤10)`:返回 `(批全文, 折叠概要)`;未读完时附带「下一批起始年份」提示。

**② fetch_events 工具 + 旧批原地折叠**(`run_progressive_agent`):

```
agent 循环 (≤80 轮):
    发给 LLM 前: compress_messages(messages)     ← 压缩副本, 本体不动
    LLM 调 fetch_events(source, start_from, start_to, limit)
        → ToolMessage 放入批全文
        → fetch_stubs 登记 (tool_call_id → 折叠概要)
        → _fold(): 除最近 keep_full_pages=2 批外, 历史批的 ToolMessage
          原地替换为折叠概要 (【人生履历 1981~1990 · 10 条 · 已折叠, 需要可重读】)
    被审核拦截 → 全部已读批折叠成占位符 → 换更小范围重试 (≤3 次)
```

上下文里**永远只有最近 2 批全文**,读过的折叠成一行——长履历下上下文长度近似常数。

**③ 双层压缩中间件**(`compression.py` + simulate 的历史管理):

```
compress_messages (无损优先):
  1. 旧 ToolMessage 长文本只留头尾 (头部通常是 id=xxx, 不丢引用)
  2. 带 tool_calls 的 AI 消息结构不动 (截断会破坏调用配对)
  3. 超预算才从最旧中间块整块丢弃 (system + 首条 human + 最近 6 块永留)

PersonaAgent 历史管理 (对话侧):
  1. 每轮 trim_messages 硬裁剪 (预算×1.5, 保头尾结构, start_on=human)
  2. 超预算×2.5 → LLM 摘要压缩: 旧消息压成「[既往对话要点]」笔记
     (保留数字/人名/未解决话题/情绪基调, 删寒暄重复)
```

硬裁剪保延迟下限,LLM 摘要保语义——两层各司其职。

### 3.6 渐进加载的收益

| 维度 | 一次性全量 | 渐进加载 |
| --- | --- | --- |
| 常驻上下文 | 全部记忆(几百 KB) | L0+骨架索引(数百 token) |
| 长履历铸造 | 超 prompt 上限 | 批次恒定长度,400+ 条无压力 |
| 检索质量 | 全量塞入, 噪音淹没 | 阈值+配额+去重后的精选块 |
| 成本 | 每轮全量 token | 按需 L2, 预算封顶 |
| 记忆演化 | 无 | 访问强化 + 时间衰减闭环 |
| 审核容错 | 大段拼接易误判 | 小批送审 + 折叠降面重试 |
