## 2. 逐项说明

### 2.1 Python 3.12 + uv workspace

**选什么**:单仓(workspace)管理五个子包,根 `pyproject.toml` 声明 `[tool.uv.workspace]`:

```
virtual_human   知识库 (ORM / 检索 / 账本, 零 LLM 依赖)
vh_generate     生成 (LLM 工具调用录入 / 骨架渐进铸造)
vh_simulate     模拟 (PersonaAgent 对话)
vh_cli          命令行 (UTF-8 终端)
vh_api          FastAPI 服务 (SSE 流式 / 后台任务)
```

**为什么**:
- 五个包**依赖单向**:`vh_api → vh_simulate → vh_generate → virtual_human`,编译期即可发现循环依赖;知识库层不 import 生成模块(嵌入通过 `register_embedder()` 依赖注入反向注册,见 `kb/retrieval.py`)。
- uv workspace 源码联动:改 `virtual_human` 立即对 `vh_api` 生效,无发版负担。
- Python 3.12 的 async 生态(psycopg async、LangChain astream)成熟。

**替代方案落选**:
- *单包平铺*:文件数上千后边界混乱,无法强制依赖方向。
- *多仓*:需要私有索引与版本号管理,单人/小团队成本高。
- *poetry/PDM workspace*:poetry 无一等 workspace 概念;uv 装速快、锁文件(`uv.lock`)可复现。

### 2.2 PostgreSQL + pgvector(而非 向量库/文档库)

**选什么**:所有数据(知识树、记忆、向量、任务、对话 checkpoint)进同一个 PostgreSQL;向量用 pgvector 的 `Vector(1024)` 列 + HNSW 索引(`vector_cosine_ops`),见 `models.py` 的 `KbEmbedding`。

**为什么**:
- **事务一致性**:骨架事件 → 情景记忆 → 财务事件必须同库同事务级联(`ondelete="CASCADE"`),混用独立向量库(Milvus/Qdrant)要自己维护双写一致性。
- **渐进加载是结构化查询**,不是纯向量检索:`get_node(load_level)`、`get_kb_tree`、账本查询都是关系查询;向量只是召回的一种信号源。
- **load_score 混合打分**需要回表读 `importance / access_count / last_accessed_at`,同库一次 join 完成。
- HNSW 十万级以下向量足够,运维零增量。
- JSONB 存半结构化 payload(`life_scaffold_events.payload`),其他方言自动退化为 JSON(`JSON().with_variant`)。

**替代方案落选**:
- *Milvus/Qdrant/Weaviate*:引入第二个有状态服务,双写一致性、备份、部署复杂度都翻倍,本项目规模收益为负。
- *SQLite*:无 pgvector、无 JSONB 高级索引,多进程后台任务并发写受限。
- *MongoDB*:关系级联弱,事务模型不如 PG 直觉。

### 2.3 SQLAlchemy 2.0 + psycopg3 async(而非 全异步驱动栈)

**选什么**:ORM 声明式 2.0 风格(`DeclarativeBase` + `Mapped[]`);同步/异步双 session 工厂(`db.py` 的 `session_factory` / `async_session_factory`);Windows 下 `run_async()` 强制 `SelectorEventLoop`。

**为什么**:
- LLM 流式(astream)与 DB IO 全异步,**对话链路不能被同步 DB 阻塞**。
- psycopg3 async 原生支持,不需要额外的 asyncpg 方言分裂。
- **Windows 兼容是硬约束**:默认 `ProactorEventLoop` 不支持 psycopg async,统一入口 `run_async()` / `main.py` 顶部切 policy,避免各处散落 workaround。
- Alembic autogenerate 以 ORM 为唯一事实来源(`models.py` → migration → `sql/schema.sql`)。

**替代方案落选**:
- *SQLModel*:与 FastAPI 作者绑定深,但复杂 CheckConstraint/Index/variant 场景仍要回落 SQLAlchemy 原生 API,等于两套心智。
- *asyncpg 直连*:放弃 ORM 后骨架/知识树这类多表级联要手写大量 SQL。
- *Tortoise/Peewee+aio*:生态与 Alembic 集成不如 SQLAlchemy 成熟。

### 2.4 LangChain + LangGraph(而非 裸 SDK / 自研循环)

**选什么**:
- `ChatOpenAI(streaming=True)` 统一 LLM 工厂(`make_llm`),OpenAI 兼容端点可切国产模型(`OPENAI_BASE_URL`)。
- **Tool-calling 为主路径**:录入/骨架生成/质检/编辑全部让 LLM 调 Pydantic 工具直接落库,不让 LLM 输出大 JSON。
- LangGraph `StateGraph` 编排骨架铸造状态机(`scaffold_graph.py`),配 `AsyncPostgresSaver` checkpointer 断点续跑。
- `trim_messages` + `count_tokens_approximately` 做对话历史裁剪。

**为什么**:
- **流式输出大 JSON 必然截断**——tool-calling 让每次产出结构化、可校验、可即时 commit,流式只用于展示文本。
- LangGraph 的 checkpointer 免费获得「任务中断可按 thread_id 续跑」,长时铸造任务(数百事件×多轮 LLM)必备。
- 消息原语(SystemMessage/HumanMessage/ToolMessage)在压缩中间件、折叠逻辑里可复用。
- 节点逻辑以 `ScaffoldHandlers` dataclass 注入,`vh_generate` 不依赖 `vh_api`(避免循环依赖)。

**替代方案落选**:
- *裸 OpenAI SDK*:工具循环、流合并(AIMessageChunk 相加)、消息裁剪全要自研,且换模型厂商成本高。
- *LlamaIndex*:以 RAG 索引为中心,本项目是「知识库 + 状态机铸造 + 工具循环」,LangChain/LangGraph 更贴。
- *自研 agent 循环*:progressive.py 里确实有一个轻量自研循环(`run_progressive_agent`)用于分页读取场景——这是**有意为之的窄用途例外**,不是主路径。

### 2.5 FastAPI + SSE(而非 WebSocket / GraphQL)

**选什么**:`vh_api` 提供 REST + SSE 流式;后台任务 `POST → job_id → 轮询 GET /api/jobs/{id}`。

**为什么**:
- LLM 生成是**单向流**,SSE 足够,自动重连/代理兼容性比 WebSocket 好。
- 长任务(铸造几分钟)不适合同步请求-响应;**job 模型**(内存态 running + jobs 表终态)让前端可轮询进度、日志、报告。
- Pydantic 请求模型与工具 schema 共用一套类型系统。
- 生命周期管理(`lifespan`):启动自检(6 项 health check)、关闭时取消后台任务 + dispose 连接池,避免 asyncio 悬挂任务。

**替代方案落选**:
- *WebSocket*:双向能力用不上,还要自建心跳/重连。
- *Celery/ARQ*:任务类型只有 ingest/check/fix/edit/scaffold 五种,`asyncio.create_task` + jobs 表足够,引入 broker 是运维负担。
- *GraphQL*:前端页面固定,无灵活拼装需求。

### 2.6 RustFS 对象存储(S3 兼容)

**选什么**:agent 文档目录挂 S3 兼容对象存储,key 约定 `{persona_id}/docs/{path}`,boto3 path-style 读写。

**为什么**:
- docx/pdf 等大文件不该进 PG `bytea`;对象存储天然按 key 隔离每个 agent 的文档命名空间。
- **S3 协议兼容**意味着未来可无缝换 MinIO/OSS/云厂商,只改 endpoint。
- RustFS 单二进制、资源占用小,本地开发 podman 一行起。
- 配置缺失时优雅降级:`docs_middleware` 不挂载文档工具,主流程不受影响。

**替代方案落选**:
- *本地文件系统*:多实例部署无法共享,无版本/覆盖语义。
- *PG 大对象*:备份膨胀,流式读取差。

### 2.7 前端 Vue 3 + Element Plus + Vite

**选什么**:9 个视图(人物列表/锻造/时间轴/质检/编辑/知识树/任务/模拟厅/文档);Element Plus 组件 + `relation-graph-vue3` 画知识图谱;`marked` 渲染 Markdown 简介。

**为什么**:
- 后台管理型界面,表单/表格/抽屉/进度条用组件库效率最高。
- 知识图谱(树边 + kb_edges 联想边)用 relation-graph 直接喂 `/api/personas/{pid}/graph` 的 nodes/edges。
- Vite 冷启动/热更新快,pnpm workspace 管理。

**替代方案落选**:
- *React*:同等组件生态下无决定性优势,团队熟悉度优先。
- *SSR 框架*:纯内控工具,无 SEO 需求。

### 2.8 可观测与健壮性约定

不是独立组件,而是贯穿的约定:

| 约定 | 实现 |
| --- | --- |
| 启动自检 | `virtual_human.healthcheck` 注册式检查(Config/DB/LLM/Embedding/Checkpointer/Storage),`/api/health` 实时重跑 |
| 任务审计 | `jobs` 表:job_type/status/percent/logs/report/result(JSONB) |
| 质检问题 | `qc_issues` 表按 severity 分级,前端红黄绿点 |
| 记忆访问 | `memory_access_log` 驱动 recency 衰减与 access 强化 |
| 配置 | pydantic-settings + dotenv,代码零 `os.environ` |
| ID | varchar(36) UUID 应用侧生成;金额 numeric(14,2) 恒正;向量 1024 维 |

## 3. 关键取舍记录(ADR 摘要)

| # | 决策 | 理由一句话 |
| --- | --- | --- |
| ADR-01 | LLM 产出走 tool-calling,不走大 JSON 输出 | 流式大 JSON 必截断;工具参数可校验可即时落库 |
| ADR-02 | 向量与关系数据同库(pgvector) | 渐进加载是结构化查询,混合打分需回表,双库一致性成本高 |
| ADR-03 | 嵌入可选、依赖注入(`register_embedder`) | 无 API Key 也能跑通全链路(词面相似度降级),依赖保持单向 |
| ADR-04 | 长任务 = LangGraph + Postgres checkpointer | 中断续跑免费获得;thread_id 按人物隔离 |
| ADR-05 | 审核拦截不 fail-fast,逐级降面(整批→逐条→模板兜底) | 单条敏感内容不应卡死整人物铸造;敏感事件黄色标记隔离 |
| ADR-06 | 大文本冷热分离(kb_nodes 无正文,正文在 contents 1:N) | L1 骨架扫描只碰热表,大字段命中才 join |
| ADR-07 | 对话上下文双层压缩(trim 硬裁剪 + LLM 摘要) | 硬裁剪保延迟下限,摘要保语义,预算来自 persona.context_token_budget |
| ADR-08 | Windows 事件循环统一入口 `run_async()` | ProactorEventLoop 不支持 psycopg async,收敛一处切换 policy |
